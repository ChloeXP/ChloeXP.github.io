Connected Components at Scale in Spark

Re-implementing CCF, a MapReduce algorithm for connected components (Kardes et al.), in Apache Spark: in PySpark and Scala, with RDDs and with DataFrames. Then benchmarking every version on web graphs growing from 10 to 5.1 million edges, to see what really drives performance: the data structure, the parallelism, or the algorithm variant.

01 · PURPOSE

Why connected components

A connected component is a group of nodes that can all reach each other: a circle of friends in a social network, a ring of linked accounts in anti-money-laundering, or all the records that describe the same real person in record linkage. Once the graph no longer fits on one machine, the computation has to be distributed.

This was a two-person course project (Université Paris Dauphine-PSL, with Laure Boizeau). The brief: understand the CCF MapReduce algorithm, implement it in Spark with both RDDs and DataFrames, in both Python and Scala, and compare the versions on graphs of increasing size.

02 · THE ALGORITHM

Everyone points to the smallest ID

CCF repeats two MapReduce jobs until nothing changes. Think of a classroom where, each round, every student tells their friends the smallest student number they know. After a few rounds, everyone in the same group knows the group's smallest number: that number becomes the component ID.

MAP
Both directions
Each edge (u, v) is emitted as (u, v) and (v, u)
SHUFFLE
Group neighbours
One adjacency list per node
REDUCE
CCF-Iterate
Find the minimum, re-attach every neighbour to it, count new pairs
DEDUP
CCF-Dedup
Drop duplicate pairs before the next round
STOP
Zero new pairs
Every node points straight to its component's minimum

Three variants were compared: Iterate only (no dedup), Iterate + Dedup ("standard"), and Iterate on a sorted neighbour list ("secondary sort").

03 · STEPS

What we did, step by step

STEP 1 · LOAD & CLEAN
Did
Loaded the SNAP web-Google (5.1 M edges) and web-NotreDame (1.5 M edges) graphs, stripped the comment header and cast node IDs to integers.
Result
5,105,039 edges, matching the file header. Scaling tests take the first N edges, from 10 to the full graph.
STEP 2 · PANDAS BASELINE
Did
Wrote the algorithm in plain Python / pandas on one machine, with a dictionary standing in for the shuffle.
Why
To validate the logic first, and to measure what Spark actually buys.
Result
Fastest below about 1,000 edges, then explodes: about 40 minutes for 100 k edges.
STEP 3 · PYSPARK RDD
Did
flatMap → distinct → groupByKey → flatMap, with an accumulator counting new pairs; a count() action triggers each round before the counter is read.
Why
The closest mapping of the paper's MapReduce jobs.
Result
About 7 s for 100 k edges.
STEP 4 · PYSPARK DATAFRAME
Did
Two versions: one with Python UDFs, one with built-in functions only (collect_set, least + array_min, explode); the sorted variant uses a window function.
Why
Built-in functions stay inside the JVM and can be optimised by Catalyst.
Result
The fastest structure on the full graphs.
STEP 5 · SCALA
Did
Same three variants with RDDs and DataFrames, run in Docker with an Apache Toree kernel and in IntelliJ with sbt.
Result
Dedup effect clearly measured; the full-graph RDD run finished but took about 80 minutes (see problems).
STEP 6 · BENCHMARK
Did
Graph size from 10 to 5.1 M edges, RDD partitions from 1 to 30, two machines and three Spark configurations; small runs repeated 3 times. Every run logged to CSV and plotted in one analysis notebook.
Result
One traceable source for every number.

Lowest at 3–5 partitions (6.4 s), close to the number of cores; beyond that, scheduling and shuffle-merge overhead grows almost linearly, to 14.7 s at 30.

Reading the results

  • DataFrames win: Catalyst rewrites the plan and Tungsten runs it in compact binary form inside the JVM, while every PySpark RDD lambda ships data to a Python worker and back.
  • Match partitions to cores: too few leaves cores idle, too many adds overhead. For large graphs, more partitions keep each one small enough for memory.
  • Dedup is the cheapest optimisation, and its gain grows with the data, as the paper predicts. Secondary sorting only matters on far larger graphs.
Data structure > partitioning > algorithm variant.
05 · PROBLEMS & FIXES

What went wrong, and what we learned

MEMORY

The full graph would not finish

On the 8 GB machine with default local[*] settings, both RDD and DataFrame runs on 5.1 M edges ran out of memory.

Fix: 50 RDD partitions made it finish (12 min), then explicit driver/executor memory, cores and spark.sql.shuffle.partitions brought it to 8.5 min.

PARTITIONS

One partition after the shuffle

coalesce was used to control DataFrame partitions, but the shuffle still produced a single partition, so the DataFrame ran single-threaded.

Fix: shuffle output is governed by spark.sql.shuffle.partitions, set in the session; a dedicated 1–30 partition sweep then picked the optimum.

COUNTERS

Accumulators inside UDFs

The "new pairs" counter, the algorithm's stop condition, did not update reliably inside DataFrame UDFs.

Fix: counted new pairs with an aggregation instead (sum(size(v) − 1), or a filtered count()), and in the RDD versions read the accumulator only after an action.

ENVIRONMENT

Running Scala Spark locally

Scala notebooks needed a Toree kernel in Docker; in IntelliJ, recent JDK module restrictions and stack overflows broke Spark at start-up.

Fix: Toree installed in the container; --add-opens, -Xss4m and heap flags in build.sbt; CCF functions moved into a Scala object so closures serialise.

REVIEW

A comparison that was not like-for-like

The first Scala DataFrame version collected the data to the driver and iterated on local collections: fast on small inputs, but not distributed.

Lesson: check where the work runs before comparing timings. A distributed rewrite was slower on small inputs and did not finish on the full graph.

OPEN

Scala RDD 10× slower than PySpark

The full-graph Scala RDD run took about 80 minutes against 8.5 for PySpark, which does not reflect the languages themselves.

Likely cause: appending to an immutable Array inside the reducer copies it every time, O(n²) on an 855 k-node component. To confirm with an ArrayBuffer rewrite.

06 · NEXT STEPS

Improvement directions

  • Lineage control: persist() each round and checkpoint() periodically, so iterations do not recompute earlier rounds or over-count accumulators.
  • A true secondary sort with repartitionAndSortWithinPartitions, instead of sorting each list in memory after groupByKey.
  • A fair Python vs Scala rerun on one machine and one configuration, with repeated full-graph runs.
  • Baselines and scale: check against GraphFrames connectedComponents(), then run on a multi-node cluster with larger graphs and handle the skew of the giant component.

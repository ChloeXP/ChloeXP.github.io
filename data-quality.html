The problem

In a modern ML workflow, a raw dataset D0 rarely goes straight into training. It passes through a chain of operations — filtering, joining, SMOTE rebalancing, encodings — before producing the final Dn. Along the way, every row may be dropped, duplicated, joined, or synthesised from other rows.

When a model misbehaves — a biased prediction, a GDPR request, an AI Act audit — one essential question becomes very hard to answer: which rows of the raw dataset produced this specific final row? This is the question data provenance (or data lineage) answers.

The project, supervised by Prof. K. Belhajjame at Dauphine-PSL, asks for a minimal viable provenance system on pandas, covering four representative operations: Filter, Oversample, Merge and Append.

What I built

A single Python module, prov.py, exposes two classes:

  • ProvenanceTensor — holds a list of scipy.sparse.csr_matrix tensors plus pandas index metadata, and provides backward(i), forward(j) and compose_chain([…]) methods.
  • Prov — a namespace of static methods, one per operation, that run the pandas call and build the matching tensor in parallel.

User-facing code barely changes: output_df, prov = Prov.filter(df, df["age"] >= 25) gives you both the filtered frame and its lineage tensor in one call.

Key design decisions

1. One list format for all operations

Every ProvenanceTensor stores its tensors as a list — length 1 for single-input ops, length N for multi-input ops. Downstream query code never has to branch on type: a single for t in self.tensors loop handles every case. The semantic difference between Append (disjunctive) and Merge (conjunctive) emerges from the pattern of non-zeros, not from a different data structure.

2. SMOTE re-implemented from scratch

The imblearn SMOTE does not expose which two parents were interpolated for each synthetic sample. Fitting an a-posteriori nearest neighbour as a “parent” is simple but mathematically wrong — the closest point need not be one of the two true parents. For a provenance project, that compromise is self-defeating. So I rewrote SMOTE in about thirty lines and recorded the two actual parents explicitly, giving a mathematically faithful tensor.

3. Tracker-column injection for Merge

Pandas does not tell you which (left row, right row) pair produced each output row, and matching by key fails on 1-to-N or N-to-N joins. Before calling pd.merge I inject a temporary column holding the positional row index into each input. Pandas propagates these columns like any other, resolving every combinatorial case. After the merge I read them back to build the tensor, then drop them. All join types (inner, left, right, full outer) are handled uniformly thanks to pandas’ native NaN behaviour on unmatched rows.

4. Positions, not labels, inside tensors

Tensors address rows by position (0..n−1), not by pandas index labels. This keeps chaining correct even when an intermediate DataFrame carries a non-contiguous index — the common case after any filter upstream.

Pipeline composition (Task 2)

For a linear pipeline D0 → [op1] → D1 → [op2] → D2 with tensors T1 and T2, the question “which raw row produced this final row” reduces to “does there exist a middle row k such that T2[i,k] = 1 and T1[k,j] = 1”. That is exactly the non-zero condition of the matrix product:

Tcomposed  =  sign( T2 · T1 )

Boolean matrix multiplication over the semiring ({0, 1}, ∨, ∧). SciPy’s sparse matmul handles the computation natively; the result is binarised. The operation is associative, so compose_chain([T1, T2, …, Tn]) is just a fold-left. Multi-input upstream ops (Merge, Append) are composed branch-by-branch, preserving the list structure through the chain.

Limitations & next steps

  • Scope. The framework covers identity-preserving / identity-changing operations. Value transformations (imputation, normalisation, one-hot encoding) are explicitly out of scope — column-level provenance would need a 4th-order tensor.
  • Linear chains only. General DAG pipelines (two parallel filters that then merge) would require a graph-aware compose_graph. The “list of tensors” structure already paves the way for this extension.
  • SMOTE performance. Brute-force k-NN is O(m² · d); on Census this runs in ∼4 s. Swapping in sklearn.neighbors.BallTree would bring it down to O(m log m · d).
  • Persistence. Tensors live in memory and export to .npz. A production backend would plug this into Parquet or DuckDB for cross-pipeline lineage queries at scale.

What I took away

Technically, I now have a hands-on grip on sparse matrix formats, SMOTE internals, and a handful of pandas edge cases that caught me off-guard (index labels vs positions, merge propagation of extra columns, concat’s positional semantics).

Methodologically, two lessons stuck. First, “think the architecture through before writing code” really pays off — the single “always a list of tensors” decision made every later extension nearly refactor-free. Second, mathematical correctness beats convenient APIs — choosing to re-implement SMOTE rather than approximate parents with imblearn is the kind of trade-off I now make deliberately in any audit-sensitive context.
